## Real-world engineering concerns
- **Concurrency:** advisory lock per contract on every transition and ledger append; unique constraints are the backstop (`UNIQUE(contract_id, seq)`, `UNIQUE(milestone_id, attempt)`, `UNIQUE(event_id)`).
- **Timestamps in hashes:** application generates `created_at` with ms precision and stores exactly that value; verification re-serializes with `isoMs`. Never use `now()` default for ledger rows.
- **Timeouts:** `statement_timeout` 15 s and `lock_timeout` 5 s inside `withTx` prevent stuck workers.
- **Idempotent jobs:** `dedupe_key` + deterministic handlers (Phases 4–5) make at-least-once delivery safe.
- **Connection limits:** pool sizes small; Render Postgres plan connection limit documented in `docs/decision-log.md`.
- **Observability:** log every `transitionContractStatus`/`transitionMilestone` at `info` with `{contract_id, from, to}`.

## Risks & blockers
| Risk | Mitigation |
|---|---|
| Drizzle can't express a constraint/trigger | Hand-write SQL in a numbered migration (already planned for triggers) |
| ms-precision mismatch breaks the hash chain | Golden test `created_at round-trips with millisecond precision`; store as `timestamptz(3)` if needed (additive migration) |
| Deadlocks from multiple locks | Only one advisory lock type (per contract); acquire it first in every transaction |
| Flaky integration tests | Single fork, `resetDb()` before each test file, no shared state |
